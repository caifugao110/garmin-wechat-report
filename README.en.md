# Garmin Daily Report

English | [简体中文](README.md)

Automatically aggregates your daily Garmin Connect health data into a Markdown report and pushes it to WeChat via [Server酱 (ServerChan)](https://sct.ftqq.com). Also ships an **interactive AI assistant for WeCom self-built apps** — chat with it directly inside the WeCom app to query your Garmin data (steps, sleep, HRV, etc.).

The Garmin authentication chain (OAuth1 → OAuth2) is implemented with plain HTTP and depends only on `fetch` and Web Crypto — no browser and no third-party Garmin SDK.

> **Note:** The pushed report, the built-in advice messages, and the AI prompt are currently written in Chinese (they target WeChat via ServerChan). To localize them, edit the strings in [src/report/formatter.ts](src/report/formatter.ts), [src/report/advice.ts](src/report/advice.ts), and the system message in [src/ai/advice.ts](src/ai/advice.ts).

## Features

- Sleep report: score, deep / light / REM / awake duration and ratios, SpO2, respiration rate
- Daily summary: steps, calories, intensity minutes, heart rate, stress, Body Battery
- Overnight physiology: HRV, baseline range, 7-day average
- Training load & recovery: training readiness, suggested recovery time, training status, VO2max, ACWR
- Weekly trend comparison against the data from 7 days ago
- **Built-in rule engine**: offline threshold-based "Today's Advice", with the most important alerts ranked first — no external service required
- **AI health analysis (optional, built in)**: set an API key for DeepSeek or any other OpenAI-compatible service, and a personalized LLM advice section is appended to the report automatically; AI failures are logged only and never block the push
- Push to WeChat via ServerChan / a WeCom group bot; failure alerts are pushed automatically when something goes wrong
- **Interactive WeCom AI assistant (optional)**: chat with your self-built app inside WeCom; the AI calls the Garmin API in real time to answer questions about steps, sleep, HRV, etc. Uses a passive-reply architecture to bypass the IP whitelist requirement of the active send API
- Four run modes: local CLI, GitHub Actions scheduled workflow, Cloudflare Workers Cron, **Tencent SCF (WeCom chat)**
- Modular report structure, easy to customize content or swap the notification channel (see guides below)

## How It Works

### Scheduled report path (local / Actions / Worker)

```
src/index.ts (Node entry)    ┐
                             ├─→ src/pipeline.ts (core orchestration)
src/worker.ts (Worker entry) ┘            │
                                          ├─ 1. garmin/auth.ts      OAuth1 → OAuth2 authentication
                                          ├─ 2. garmin/api.ts       fetch sleep / summary / HRV / training data
                                          ├─ 3. report/formatter.ts render Markdown
                                          │      └─ report/advice.ts rule engine → "Today's Advice"
                                          ├─ 4. ai/advice.ts        (optional) LLM call → "AI Health Advice"
                                          └─ 5. notify/             ServerChan / WeCom push
```

### WeCom chat path (Tencent SCF)

```
WeCom server POST /wecom/callback
         │
         ▼
src/scf/handler.ts ──→ src/wecom/callback.ts ──→ src/wecom/crypto.ts (verify sig + decrypt)
         │
         ▼
src/wecom/chat.ts (LLM main loop with tool_call dispatch)
         │
         ├── src/garmin/auth.ts + api.ts ── real-time Garmin query
         └── src/wecom/crypto.ts ── encrypt passive-reply XML → return directly in POST response
```

The chat path uses a **passive-reply architecture**: instead of calling the WeCom active-send API (which requires an egress IP in the "trusted IP" whitelist — `errcode=60020`), the reply is encrypted and returned directly in the POST callback response. Zero outbound calls, completely bypassing the IP whitelist. See the architecture note in the SCF deployment section for details.

## Deploy with GitHub Actions (Recommended)

In your fork, go to:

**Settings → Secrets and variables → Actions → (lower on the page) Repository secrets → New repository secret**

Add the following secrets one by one (names must match exactly and are case-sensitive):

| Secret name | Required | Value |
| --- | --- | --- |
| `GARMIN_USERNAME` | One of two | Your Garmin login email |
| `GARMIN_PASSWORD` | One of two | Your Garmin password |
| `GARMIN_OAUTH1_TOKEN` | One of two (recommended) | Token from running `npm run token` locally |
| `GARMIN_OAUTH1_TOKEN_SECRET` | With token | Secret from running `npm run token` locally |
| `SERVERCHAN_SENDKEY` | Recommended | ServerChan SendKey; if omitted the job runs without pushing |
| `WECOM_BOT_KEY` | No | WeCom group bot webhook key; when set, an extra copy is pushed to the WeCom group |
| `AI_API_KEY` | No | Enables AI health analysis; if unset the report has no AI advice section |

In other words, **username+password** and **OAuth1 token** are two alternative credential sets. The token approach is recommended (see the risk-control section below for why). Once configured, your secret list should look like:

```
GARMIN_OAUTH1_TOKEN
GARMIN_OAUTH1_TOKEN_SECRET
GARMIN_PASSWORD

SERVERCHAN_SENDKEY
# Optional:

```

Notes about Repository secrets:

- Once saved, a secret **can only be updated, never viewed again**. Click the pencil icon to update it and the trash icon to delete it.
- Secrets are encrypted at rest, injected into the workflow only as environment variables, and automatically masked in logs; they never appear in the code.
- Credentials must go in **Secrets** (encrypted), not **Variables** (plaintext). Use **Variables** only for non-sensitive configuration.
- The workflow [.github/workflows/daily-report.yml](.github/workflows/daily-report.yml) references them via `${{ secrets.XXX }}` and includes a credential pre-check: the job fails immediately with a clear message when neither credential set is configured.

### Step 3: Verify with a manual run

1. Open the **Actions** tab and select **Garmin Daily Report** on the left.
2. Click **Run workflow** on the right to trigger one run.
3. Click into the run record to inspect each step's logs. On success you should receive the report on WeChat; on failure, follow the log messages (see FAQ at the end).

### Step 4: Automatic scheduled runs

After a successful verification, nothing else is needed — the workflow runs on a cron schedule:

```yaml
on:
  schedule:
    - cron: '40 23 * * *'   # primary: 23:40 UTC = 07:40 Beijing time (next day)
    - cron: '50 23 * * *'   # backup:  23:50 UTC = 07:50 Beijing time (next day)
  workflow_dispatch:        # keep manual triggering
```

Notes:

- There are two scheduled triggers each day: **07:40 Beijing time (primary) and 07:50 (backup)**. At startup the workflow calls the GitHub API to check whether a **successful** scheduled run already exists in the last 12 hours: if so, the backup trigger skips automatically so the report is never pushed twice; if the primary run fails, is delayed, or is dropped by GitHub, the backup sends it instead. Manual runs (workflow_dispatch) are not affected by this check.
- GitHub Actions cron uses **UTC**; Beijing time = UTC + 8. To change the push time, edit the cron in [.github/workflows/daily-report.yml](.github/workflows/daily-report.yml). For example, `0 0 * * *` is 08:00 Beijing time and `0 22 * * *` is 06:00.
- Scheduled runs are not guaranteed to start exactly on time; delays of a few to tens of minutes are possible during peak hours, and in rare cases a scheduled run is dropped entirely — this is why the backup trigger exists.
- GitHub automatically pauses scheduled workflows in repositories with no commit activity for 60 days; re-enable it on the Actions page or push a commit to resume.

### Important: Garmin blocks GitHub Actions logins

`sso.garmin.com` sits behind Cloudflare and frequently blocks IPs from cloud datacenters such as GitHub Actions runners. Typical errors are
`SSO login failed: _csrf token not found`, `403`, or `429`. This project provides a token-based direct login that bypasses SSO:

```bash
# Run on your own machine (with username/password configured in .env) to complete a normal login
npm run token
```

The script prints `GARMIN_OAUTH1_TOKEN` and `GARMIN_OAUTH1_TOKEN_SECRET`.
Add them as repository Actions Secrets (steps above). CI then talks only to `connectapi.garmin.com` to exchange the token for a session and never touches the risk-controlled SSO site.

Notes:

- The token is long-lived and equivalent to your account credentials — never commit it to the repository or leak it.
- If CI reports authentication failures again later, re-run `npm run token` and update the Secrets.
- The workflow includes a credential pre-check step that reports exactly which variable is missing.

### How to disable / pause GitHub Actions

Choose one of the following (after disabling, no Garmin requests are made; Secrets can be kept or deleted):

1. **Pause temporarily and resume later (recommended)**: open **Actions** → select **Garmin Daily Report** on the left → the `⋯` menu in the top-right → **Disable workflow**. Use **Enable workflow** in the same place to resume.
2. **Keep only manual triggering, remove the daily schedule**: edit [.github/workflows/daily-report.yml](.github/workflows/daily-report.yml), remove the entire `on.schedule` block and keep only `workflow_dispatch:`, then commit and push.
3. **Remove completely**: delete the file `.github/workflows/daily-report.yml` and push; the workflow disappears permanently.
4. **Disable Actions for the whole repository**: **Settings → Actions → General → Actions permissions** → **Disable actions**.

1. **Stop only the daily cron, keep manual `/run`**: edit [wrangler.toml](wrangler.toml), empty the `crons` entry under `[triggers]` (`crons = []` or remove the whole section), then re-run `npm run deploy` to apply. ## Deploy on Tencent Cloud SCF (WeCom Chat Bot)

> Why Tencent SCF? Cloudflare's free `*.workers.dev` domain is blocked on mainland China networks, so WeCom's verification server (which runs inside China) cannot reach a callback on that domain. Additionally, Cloudflare Workers' egress IP pool is unpredictable and can't be added to WeCom's "trusted IP" whitelist — which is mandatory for the active send API. Tencent SCF is in the same ecosystem as WeCom, comes with a mainland-reachable HTTPS address out of the box, and is the best place for the chat callback.

### Architecture: passive reply vs. active send

WeCom self-built apps have two ways to reply to users:

| Approach | How it works | Pros | Cons |
| --- | --- | --- | --- |
| **Active send** | Return `success` in the POST response, then call `POST /cgi-bin/message/send` asynchronously | Not limited by the 5-second timeout | **Requires the caller's egress IP to be in WeCom's "trusted IP" whitelist** (`errcode=60020`). Cloudflare Workers' IP pool is too large; Tencent SCF's NAT pool is flagged as a "third-party service provider IP" and cannot be whitelisted either |
| **Passive reply** | Process the chat synchronously inside the POST callback and return an encrypted reply XML directly | **Zero outbound calls; completely bypasses the IP whitelist** | Must finish within 5 seconds (LLM + Garmin hot path is 2–5 seconds, well within budget in practice) |

This project uses the **passive-reply architecture** for the chat path. Message encryption uses AES-256-CBC with 32-byte-block PKCS7 padding (Web Crypto auto-appends a 16-byte block which is manually trimmed), and signing uses SHA-1 — all implemented in [src/wecom/crypto.ts](src/wecom/crypto.ts).

### Troubleshooting

- **Callback URL still fails to save**: use `/diag` to confirm the SCF is running; double-check the `/wecom/callback` path; check the Tencent SCF log query page for inbound requests
- **Chat replies are missing / stale Garmin data**: the OAuth1 token may have expired — re-run `npm run token` and update the environment variables
- **Replies are truncated**: WeCom passive replies have a 4096-byte limit; truncate AI output in `handleUserMessage` if needed
- **Duplicate replies from retries**: same-instance MsgId deduplication is built in (60s TTL); WeCom does not retry POST callbacks once the passive reply arrives within 5 seconds
- **workers.dev is unreachable from mainland**: this is a network block, not a code bug. The scheduled-report Worker is fine (ServerChan pushes are one-way egress), but the chat callback needs a mainland platform — Tencent SCF is the recommended choice

## Customizing the Push Content

### Adjusting the report body

Every report section lives in [src/report/formatter.ts](src/report/formatter.ts), split into independent functions:

| Function | Report section |
| --- | --- |
| `formatSleepSection` | Sleep (last night) |
| `formatDailySection` | Daily health summary |
| `formatHealthSection` | Overnight physiology (HRV) |
| `formatTrainingSection` | Training load & recovery |
| `formatTrendsSection` | Weekly trend comparison |
| `formatAdviceSection` | Today's advice (calls the rule engine in [src/report/advice.ts](src/report/advice.ts)) |
| `formatReport` | Assembles the whole report; reorder or add/remove sections here |

The helper `row(label, value, suffix)` emits a `- label: value` line; the enum-to-label maps (such as `QUALIFIER_MAP`, `STATUS_MAP`, `ACWR_MAP`) are also defined at the top of the file and can be reworded directly.

Simple example: the API already fetches "basal metabolic calories" but the report does not show it. Just add a few lines in `formatDailySection`:

```ts
if (d.bmrKilocalories !== null) {
  lines.push(row('基础代谢', String(d.bmrKilocalories), ' kcal'));
}
```

Preview locally with `DRY_RUN=1 npm start` (see [.env.example](.env.example)).

### Changing the title

The push title is in [src/pipeline.ts](src/pipeline.ts):

```ts
const title = `Garmin 日报 ${date}`;
```

Note that ServerChan's `title` must not contain line breaks.

### Push parameters or a different notification channel

Push logic is concentrated in `pushReport(sendKey, title, desp)` in [src/notify/ftqq.ts](src/notify/ftqq.ts):

- To use ServerChan's multi-channel selection, append its optional parameters (e.g. `channel`) to the request body; refer to the [ServerChan docs](https://sct.ftqq.com/docs/) for valid values.
- To switch to Bark / WeCom / Lark / Telegram / DingTalk, create a new notifier modeled on `ftqq.ts` (export a function accepting `(title, content)`) and replace the `pushReport` calls in [src/pipeline.ts](src/pipeline.ts). For example, Bark is just:

```ts
export async function pushBark(deviceKey: string, title: string, content: string) {
  await fetch(`https://api.day.app/${deviceKey}/${encodeURIComponent(title)}/${encodeURIComponent(content)}`);
}
```

### Error notification text

On authentication failure or task exception, [src/pipeline.ts](src/pipeline.ts) and [src/index.ts](src/index.ts) push "login failed" / "task exception" notifications; edit the title and body strings at those call sites to change them.

## Reading the Data: Metrics & Reference Advice

The report only presents data. Below are common reference ranges and actions for each metric so you can judge your daily status yourself. **Individual variation is large — the most valuable comparison is against your own baseline (and the weekly trends). The following is general health knowledge, not medical advice.**

### Sleep

- **Total duration**: 7–9 hours is generally recommended for adults. Consistently below 6 hours accumulates sleep debt; keep a fixed bedtime and reduce caffeine and screen blue light before sleep.
- **Sleep score**: Excellent/Good is fine; single-day fluctuations are normal. Investigate irregular schedule, alcohol, or late dinners only when scores trend down for several days.
- **Stage ratios**: for healthy adults, deep sleep is roughly 13%–23% and REM about 20%–25%. Low deep sleep is commonly linked to alcohol before bed, late bedtime, or fragmented sleep; low REM often tracks insufficient total duration (REM concentrates in the second half of the night).
- A high **awake ratio** means frequent awakenings — check room temperature, noise, and pre-sleep stress.
- Elevated **sleep stress** and poor overnight Body Battery charging indicate poor sleep quality; reduce the day's load even if you spent enough time in bed.

### Heart rate & HRV

- **Resting heart rate (RHR)**: compare with your own usual level. A morning RHR more than 5–10 bpm above baseline often signals fatigue, stress, alcohol, or the early stage of a cold — reduce training intensity that day.
- **Overnight HRV**: never compare with others; watch the `baseline range`. Multiple days below baseline (status "unbalanced / low") usually mean insufficient recovery or accumulated stress; single-day swings are not concerning.
- HRV rebounding and RHR falling back is a positive sign that recovery is complete.

### Stress & Body Battery

- Chronically high **average stress** with little Body Battery **charge / high drain**: add relaxation and naps; review sleep and caffeine intake.
- Waking Body Battery consistently below 50 indicates inadequate overnight recovery — postpone high-intensity workouts.

### Training load & recovery

- **Training readiness**: a high score (typically ≥80) suits hard sessions or races; Moderate suits regular training; Low / Very Low calls for recovery activity: walking, easy cycling, stretching.
- **Suggested recovery time**: estimated by Garmin from your last hard effort; avoid stacking more hard sessions before it resets.
- **ACWR (acute:chronic workload ratio)**: the commonly used empirical safe zone is about 0.8–1.5. "Very high" raises short-term injury risk — reduce volume; chronically "very low" means insufficient stimulus and possible detraining.
- **Training status**: consecutive "Overreaching / Strained" calls for a deload week; "Detraining" means you should return to regular training.
- **VO2max**: look at the long-term trend (weeks). A steady slow rise signals improving cardio fitness; a sudden short-term dip first suggests fatigue or poor sleep.

### Blood oxygen (SpO2)

Healthy adults typically average above 94% at night. Watches can be thrown off by strap tightness and sleeping position, so **an occasional low reading is not alarming; however, if readings repeatedly and stably fall below 90%, re-measure with a medical device and consult a doctor**.

### Summary

- Observe a single-day anomaly first; act on **2–3 consecutive days moving in the same direction**.
- In the weekly trend table, HRV ↓ + RHR ↑ + sleep score ↓ appearing together is a clear "rest now" combination.
- When feeling unwell, prioritize subjective feelings over step and intensity-minute goals.

## Today's Advice: Built-in Rule Engine and Optional AI Analysis

The "Today's Advice" section at the end of the report is generated offline by the **built-in rule engine** by default, without any external service. On top of that, the project ships with **optional, built-in AI analysis**: once an API key is configured, a personalized natural-language paragraph produced by an LLM is appended after the rule-based advice. They coexist by default (rules first, AI second), and either one can be disabled if you prefer.

### Built-in rule engine (enabled by default, offline)

The rule engine lives in [src/report/advice.ts](src/report/advice.ts) as a pure function: it takes the structured `ReportData`, returns an array of advice strings, and `formatAdviceSection` renders them as the final report section. It makes no network calls, sends no data anywhere, and costs nothing; behavior is identical on Node and Cloudflare Workers.

Built-in rules (trigger → advice):

| Metric | Trigger | Advice |
| --- | --- | --- |
| SpO2 | Overnight / daily minimum < 90% | Re-measure with a medical device and consult a doctor (top priority) |
| HRV | Below personal baseline range, or status `UNBALANCED` | De-stress, sleep early, avoid stacking hard sessions |
| Training readiness | < 50 / ≥ 80 | Focus on recovery activity / good day for high-quality hard training |
| ACWR | > 1.5 (or HIGH/VERY_HIGH) / < 0.8 (or LOW/VERY_LOW) | Reduce load to prevent injury / gradually increase training |
| Training status | `OVERREACHING` / `STRAINED` | Schedule a deload week |
| Body Battery | Overnight charge < 50 | Postpone high-intensity training |
| Resting HR | Up ≥ 5 bpm vs 7 days ago | Watch for fatigue, stress, or early illness |
| HRV trend | Down > 15% vs 7 days ago | Reduce load |
| Sleep duration | Under 6 hours; or down ≥ 1.5 hours vs 7 days ago | Take a nap and go to bed earlier |
| Sleep score | < 60 | Check schedule, alcohol, pre-sleep stress |
| Sleep structure | Deep ratio < 13% / REM < 18% / awake > 10% | Targeted sleep-hygiene improvements |
| Sleep stress | > 40 | Lower today's exercise intensity |
| Average daily stress | > 50 | Breathing exercises, cut caffeine |
| Steps | Under 50% of goal | Take a 20–30 minute post-meal walk |
| All normal | No rule fires | One positive summary line |

Other design details:

- Every tip carries a priority (SpO2 alerts > recovery/training > sleep/stress > activity/trends > positive feedback); tips are sorted by priority and capped at 6 (`MAX_TIPS`) so the most important reminders are never buried.
- When every data endpoint for the day fails and no data is available, the section is hidden automatically — no empty block appears.
- The section always ends with a disclaimer stating that advice is generated locally from fixed thresholds, for reference only, and is not medical advice.

**Adjusting thresholds or adding rules**: edit [src/report/advice.ts](src/report/advice.ts) directly, following the existing `if` blocks to `push({ priority, text })` into the `tips` array. Available fields are listed in [src/report/types.ts](src/report/types.ts). The thresholds are generic references — tune them to your own baseline (for example, if your RHR is naturally above 70, do not use the fixed threshold; rely on the comparison-against-7-days/baseline rules instead). Run `npm run typecheck` and `DRY_RUN=1 npm start` after changes.

**Disabling the rule engine**: remove the few lines calling `formatAdviceSection` inside `formatReport` in [src/report/formatter.ts](src/report/formatter.ts) (and the top-of-file `import { generateAdvice } ...`). No other files need to change.

### AI health analysis (optional, built in)

On top of the offline rule-based advice, the project has **built-in** LLM (AI) analysis: after the Markdown report is rendered and before it is pushed, the full report is sent to any OpenAI-compatible service. The model returns 3–5 short bullet points focused on metrics that clearly deviate from your personal baseline, and they are appended to the report as an "AI Health Advice" section. The call lives in [src/ai/advice.ts](src/ai/advice.ts) and is mounted in [src/pipeline.ts](src/pipeline.ts) right after `formatReport`. It uses native `fetch` with no SDK and runs on both Node and Workers.

**How to enable it**: just set `AI_API_KEY`. When it is unset, the entire AI step is skipped and behavior is identical to the rule-engine-only setup.

| Variable | Required | Default | Description |
| --- | --- | --- | --- |
| `AI_API_KEY` | Required to enable | — | Provider API key; if unset, AI is never called |
| `AI_BASE_URL` | No | `https://api.deepseek.com` | OpenAI-compatible endpoint (note some providers require the `/v1` suffix) |
| `AI_MODEL` | No | `deepseek-chat` | Model name |

Common compatible providers:

| Provider | `AI_BASE_URL` | Example `AI_MODEL` |
| --- | --- | --- |
| DeepSeek | `https://api.deepseek.com` | `deepseek-chat` |
| Qwen (Tongyi) | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| Moonshot Kimi | `https://api.moonshot.cn/v1` | `moonshot-v1-8k` |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |

**Configuration for each run mode** (everything is already wired in code — no code changes needed):

- **Local run**: fill in the three variables in `.env` — [.env.example](.env.example) already includes them, and [src/index.ts](src/index.ts) reads them and passes them into `runPipeline` automatically.
- **GitHub Actions**: add `AI_API_KEY` under **Settings → Secrets and variables → Actions** (also add `AI_BASE_URL` / `AI_MODEL` if you switch providers). The **Run report** step in [.github/workflows/daily-report.yml](.github/workflows/daily-report.yml) already passes all three variables through, so the next run picks them up with no workflow edits.
- **Cloudflare Workers**: run `npx wrangler secret put AI_API_KEY`; `AI_BASE_URL` and `AI_MODEL` are pre-declared in the `[vars]` section of [wrangler.toml](wrangler.toml) — edit the defaults there, and [src/worker.ts](src/worker.ts) already reads them.

**Behavior and customization**:

- If the AI API times out, returns an error, or returns empty content, the failure is only written to the run log (a line starting with `[pipeline] AI 分析失败，跳过`) — it **never blocks report generation or the WeChat push**.
- The AI section always ends with a disclaimer: generated by AI, for reference only, not medical advice.
- To change the analysis style, number of points, or the prompt: edit the system message and `temperature` in [src/ai/advice.ts](src/ai/advice.ts).
- To **replace** the rule-based advice with AI instead of appending to it: remove the `formatAdviceSection` call from `formatReport` in [src/report/formatter.ts](src/report/formatter.ts).

> Privacy note: with AI enabled, your health data (the full report text) is sent to a third-party AI provider — review their privacy policy first. The report itself contains no personally identifying information such as your name; if you want stricter control, trim the report content in [src/pipeline.ts](src/pipeline.ts) before calling `generateAdvice`.

### Core data flow

**Scheduled report path**:

1. An entry reads environment variables, builds a `PipelineConfig`, and calls `runPipeline` ([src/pipeline.ts](src/pipeline.ts)).
2. `GarminAuth` completes authentication (username/password via SSO; or direct exchange when a token is present).
3. `GarminApi` fetches the day's five data sets **concurrently** with `Promise.allSettled`; one endpoint failing does not affect the other sections (the error goes into the `xxxError` field and the section shows "fetch failed").
4. It then fetches the data from 7 days ago and computes weekly trends with `buildTrend`.
5. `formatReport` renders the Markdown and appends "Today's Advice" from the rule engine; if `AI_API_KEY` is set, [src/ai/advice.ts](src/ai/advice.ts) then appends an "AI Health Advice" section (AI failures are logged only and do not block the push); finally `pushReport` sends the report to ServerChan / WeCom.

**WeCom chat path**:

1. WeCom sends a POST to `/wecom/callback` containing encrypted XML.
2. `verifySignature` checks the signature → `decryptMessage` decrypts the XML.
3. `handleUserMessage` enters the LLM main loop: parse intent → call Garmin API on demand (steps / sleep / HRV / training) → return a natural-language reply.
4. `buildTextReplyBodyXml` builds the reply message body XML → `encryptMessage` encrypts it → wrap in outer XML (Encrypt + MsgSignature + TimeStamp + Nonce) → return directly as the POST response body.

### Full path for adding a new metric

Using a new "hydration" section as an example, change 5 files in data-flow order:

1. **Add the endpoint path** — [src/garmin/endpoints.ts](src/garmin/endpoints.ts):

   ```ts
   hydration: (date: string) =>
     `/usersummary-service/usersummary/hydration?calendarDate=${date}`,
   ```

2. **Add types** — [src/report/types.ts](src/report/types.ts): define a `HydrationData` interface and add `hydration: HydrationData | null` plus `hydrationError: string | null` to `ReportData`.

3. **Add request and parsing** — [src/garmin/api.ts](src/garmin/api.ts): write `getHydration(date)` modeled on `getSleep`; first define a `RawXxx` interface containing only the fields you need, normalizing missing values to `null`.

4. **Wire into orchestration** — [src/pipeline.ts](src/pipeline.ts): add `api.getHydration(date)` to the `Promise.allSettled([...])`, split value and error with the same `settled()` helper, and put them into `reportData`.

5. **Render** — [src/report/formatter.ts](src/report/formatter.ts): write `formatHydrationSection(data)` (check `hydrationError` first, then empty data) and insert it where you want in `formatReport`.

If you only want to "show an existing field / reword something", only step 5 is needed (see the basal-metabolism example above).

### Runtime compatibility constraints

- Shared code under `src/` runs on both Node and Cloudflare Workers, so **use only cross-platform capabilities** such as `fetch`, Web Crypto, and `Intl`. Do not import `node:fs`, `node:process`, etc.; such usage is allowed only in [src/index.ts](src/index.ts) and `scripts/`.
- The project is ESM; relative imports must carry the `.js` suffix (e.g. `import { GarminAuth } from './garmin/auth.js'`) even though the source is `.ts`.
- Garmin field shapes can change; be tolerant of missing fields when adding parsers (`?? null`) so the whole task never crashes.

## FAQ

**I get "Garmin report login failed: no ticket"?**
Wrong username/password, two-factor authentication enabled, or the login IP is risk-controlled. Log in once in a local browser to confirm account status; in CI switch to the OAuth1 token approach above.

**I get HTTP 429?**
You are logging in too frequently and got rate-limited. Wait a while before triggering again and avoid repeated manual runs; if both Actions and Workers are deployed, stagger their cron times.

**Actions succeeds but I receive no WeChat push?**
Check that `SERVERCHAN_SENDKEY` is correct and not expired; the job logs print "push result: success / failure reason". Locally, set `DRY_RUN=1` to confirm the report itself generates correctly.

**There are no scheduled run records on the Actions page?**
Check whether the workflow is Disabled; forks require enabling Actions once; GitHub auto-pauses scheduled workflows after 60 days of inactivity — push a commit or re-enable to resume.
A backup trigger is configured for 07:50: if the 07:40 primary trigger is dropped by GitHub, the backup detects that no successful run exists today and sends the report automatically; if neither time shows any run record, go through the checks above.

**Some sections show "fetch failed" or N/A?**
A single endpoint failure does not affect other data. It may be that the data for that day has not synced yet (too early in the morning, watch not synced), or Garmin changed the API fields. Try backfilling a historical date with `?date=`; if it keeps failing, review the field parsing in [src/garmin/api.ts](src/garmin/api.ts).

**WeCom callback URL fails to save with "request not passed"?**
The most common cause is that your callback domain is unreachable from mainland China. The free `*.workers.dev` domain is blocked on mainland networks, so WeCom's verification server cannot connect. You must use a mainland-reachable platform: Tencent SCF (recommended — same ecosystem as WeCom, comes with a mainland HTTPS address out of the box), Alibaba Cloud Function Compute, or your own server. See the Tencent SCF deployment section above.

**WeCom send API returns errcode=60020 "not allow to access from your ip"?**
This is the IP whitelist restriction when using the active send API. Cloudflare Workers' egress IP pool is unpredictable, and Tencent SCF's NAT pool is flagged as a "third-party service provider IP" and cannot be whitelisted either. This project's chat path uses a **passive-reply architecture** (return encrypted XML directly in the POST response), which does zero outbound calls and completely bypasses this limitation. If you still hit 60020 elsewhere, either switch to passive reply or bind a fixed public IP to your send-API server and add it to the whitelist.

**Tencent SCF code update not taking effect?**
After re-uploading the zip you need to click **Save** for it to apply. If in doubt, check the latest run logs in the SCF console or open `/diag` to confirm the SCF is healthy and environment variables are present.
